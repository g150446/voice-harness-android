# ジェスチャー誤発火と発話ゲート

2026-08-31、内科外来中（10:00–12:00）の録音開始4件が全て誤発火であることをユーザーが確認した。
その解析結果と、Android 側に入れた対策の記録。

## 解析: 閾値では分離できない

端末の履歴100件（`shared_prefs/voice_history_prefs.xml`、各エントリに FW ジェスチャー診断が
添付されている）を Tailscale 経由の adb で取得して解析した。

現行ゲート（`0.0.72` 相当）の正検出10件（08-30以降）との比較:

| 特徴量（FW閾値） | 誤発火4件 | 正検出10件 |
|---|---|---|
| match `+imp`（≥0.65） | 0.665–1.193 | 0.693–2.883 |
| match `phi`（≥140°） | 174–180° | 145–180° |
| lift `+imp`（≥0.30） | 0.340–0.394 | 0.302–0.601 |
| `xy` 比（≥0.42） | 0.548–1.053 | 0.291–2.734 |
| final hold（≥500ms） | 500–502 | 500–526 |

`final_hold_start` 回数、hold 中断回数、`lift_near_miss` 数、hold 中 max RMS も全て正検出の
分布内に収まる。境界的な重なりではなく**完全な包含**である。

**したがって FW 閾値の引き上げは打ち手にならない。** `0.0.68`（lift imp 0.30）、
`0.0.72`（match 0.65 / 140°）と2度ラチェットを上げてきたが、この軸は尽きている。
どれを上げても正検出が同数落ちる。次にこの周辺を触る人は、まずこの表を再現してから
閾値に手を付けること。

### 原因: ジェスチャー定義が日常動作と同一

`harness-node/docs/flex_pronation_gesture.md` の定義は「手の甲側に装着 → 水平静止0.5秒 →
口元へ挙上 → 手首を返して掌下で500ms静止」。デバイスは手の甲側にあるので、返した先は
**腕時計の文字盤を見る姿勢そのもの**。しかも同ドキュメントが明記するとおり FW は
「加速度だけで水平な掌上/掌下を絶対判別できない」ため、**回す向きすら区別できない**
（掌下→掌上に反転させても FW から見た信号は同じで、対策にならない）。

聴診・触診・カルテ記載はこの動作を1日に何十回も含む。2時間で4件という頻度と一致する。

## 対策: 発話ゲート（`UtteranceIntentGate`）

録音と ASR は従来どおり走らせ、書き起こしが「アシスタントへの依頼」でなければ
**LLM 呼び出しと TTS 発話に到達させない**。診察室での実害は、マイクが開くことではなく
無関係な応答が読み上げられることだった（誤発火4件のうち3件が応答を生成・発話していた）。

### 極性の設計

**非依頼の積極的証拠があるときだけ抑制する。** 「依頼に見えなければ抑制」ではない。
後者だと想定しなかった言い回しを黙って潰すため、未知の日本語表現は既定で通す設計にした。

判定順（`app/src/main/java/com/g150446/voiceharness/UtteranceIntentGate.kt`）:

1. 依頼形・疑問形・アプリコマンド語・会話リセット句 → **無条件 PASS**。
   `ですか` は疑問形に含めるが `です` は含めない（「お疲れ様です」を通してしまうため）。
2. CJK が皆無 かつ 音声言語設定が `JAPANESE` → `SUPPRESS_NON_CJK`。
   日本語運用での英字のみの書き起こしは Whisper の無音幻聴。`ENGLISH` / `AUTO` では適用しない。
3. 相槌のみ（最長一致で全体を消費できる） → `SUPPRESS_BACKCHANNEL`。
   ただし会話セッションが継続中なら PASS（問い返しへの「はい」を守る）。
4. CJK 10文字以下で格助詞終端 → `SUPPRESS_FRAGMENT`。
5. それ以外は PASS。

セッション継続判定は `AssistantGateway.isConversationActive()`（10分窓）。
**抑制された発話は LLM を呼ばないのでターンを追加せず、セッションを開かない。**
誤発火が次の誤発火の相槌免除を誘発する連鎖は構造的に起きない。

### 組み込み位置

`VoiceProcessor.transcribeAndRespondOnDevice()`、`AsrTextFilter.isGarbageOrEmpty` の直後。
呼び出し元はジェスチャー録音経路のみで、`handleAssistantRequest`（システムアシスタント／
テキスト入力）は通らない。

抑制時は履歴に `errorMessage = "誤発火として抑制: <Verdict>"` を残し、
**書き起こしテキストは消さない**。何を誤認したか追えないとゲートを調整できない。

### 実データによる検証

履歴100件のうち無音を除く54件（意図的コマンド32件 / 非意図22件）を実装コードに通した:

```
blockedIntent=0 / 32     passedJunk=0 / 22
  SUPPRESS_NON_CJK      18   ("I'm going to go." "All right." "Thank you." "I'm sorry." "PHONE RINGS")
  SUPPRESS_BACKCHANNEL   2   (「はい、はい。」「はい、お疲れ様です。どうも。」)
  SUPPRESS_FRAGMENT      2   (「老廃物を」「もう本当に」)
```

**この検証の限界**: 抑制側22件のラベルは表層特徴（英語・擬音・相槌・断片）で人手判定
しており非循環。通過側32件のラベルはキーワード族がゲートと重なるため循環がある。
ゲートが「証拠がなければ通す」設計であることが唯一の担保なので、
**外来1日運用で誤遮断0件を確認するまでが本当の合格判定**。履歴の
`誤発火として抑制:` を後から grep して確認できる。

### 既知のリスク

`SUPPRESS_FRAGMENT` は「明日の天気は」のような短い実クエリを潰しうる（CJK 6文字、
格助詞 `は` 終端）。`？` が付けば疑問形で通る。誤遮断が出たら
`FRAGMENT_MAX_CJK` を下げるか、助詞集合から `は` `が` を外す。

## 残った課題

誤発火そのものは止まっていない（マイクは開き、ASR は走る）。根本対策には
IMU 生時系列を使った分類が要る。FW には既に軌跡パイプライン（`0x36`/`0x37`/`0x38`、
40 Hz × 6軸 × 9.6秒窓）が実装済みだが `#if GESTURE_DEBUG_HISTORY`（既定 0）で
本番ビルドから落ちている。成功時の flush は録音停止処理の中にあり音声と競合せず、
ASR 完了前に届くため、**発話ゲートと同じ判定点で分類器の判定を使える**。

必要なのはラベル付きデータで、今は1件も無い。収集基盤（実行時フラグでの軌跡有効化、
Android 側のパースとファイル保存、履歴画面でのラベリング）が次の作業。
学習後の Go/No-Go は「正検出維持率95%で誤発火70%以上削減」に置く。達成できなければ
ML では分離できないと結論し、ジェスチャー定義そのものの変更を検討する。
