# ジェスチャー誤発火と発話ゲート

2026-08-31、内科外来中（10:00–12:00）の録音開始4件が全て誤発火であることをユーザーが確認した。
その解析結果と、Android 側に入れた対策の記録。

> **2026-09-04 追記:** 閾値では分離できない結論を受け、日常利用ではジェスチャー自体を
> **既定オフ（タップのみ）** にした。FW `0.0.95` の検出スイッチ（RX `0x07`）と
> アプリの「ジェスチャー録音」Switch。詳細は
> [`gesture_detect_default_off.md`](gesture_detect_default_off.md)。
> 発話ゲート・IMU 軌跡収集（学習用）は引き続き有効。

## 解析: 閾値では分離できない

端末の履歴100件（`shared_prefs/voice_history_prefs.xml`、各エントリに FW ジェスチャー診断が
添付されている）を Tailscale 経由の adb で取得して解析した。

現行ゲート（`0.0.72` 相当）の正検出10件（08-30以降）との比較:

| 特徴量（FW閾値） | 誤発火4件 | 正検出10件 |
|---|---|---|
| match `+imp`（≥0.65） | 0.665–1.193 | 0.693–2.883 |
| match `phi`（≥140°） | 174–180° | 145–180° |
| lift `+imp`（≥0.30） | 0.340–0.394 | 0.302–0.601 |
| `xy` 比（≥0.42） | 0.548–1.053 | 0.291–2.734 |
| final hold（≥500ms） | 500–502 | 500–526 |

`final_hold_start` 回数、hold 中断回数、`lift_near_miss` 数、hold 中 max RMS も全て正検出の
分布内に収まる。境界的な重なりではなく**完全な包含**である。

**したがって FW 閾値の引き上げは打ち手にならない。** `0.0.68`（lift imp 0.30）、
`0.0.72`（match 0.65 / 140°）と2度ラチェットを上げてきたが、この軸は尽きている。
どれを上げても正検出が同数落ちる。次にこの周辺を触る人は、まずこの表を再現してから
閾値に手を付けること。

### 原因: ジェスチャー定義が日常動作と同一

`harness-node/docs/flex_pronation_gesture.md` の定義は「手の甲側に装着 → 水平静止0.5秒 →
口元へ挙上 → 手首を返して掌下で500ms静止」。デバイスは手の甲側にあるので、返した先は
**腕時計の文字盤を見る姿勢そのもの**。しかも同ドキュメントが明記するとおり FW は
「加速度だけで水平な掌上/掌下を絶対判別できない」ため、**回す向きすら区別できない**
（掌下→掌上に反転させても FW から見た信号は同じで、対策にならない）。

聴診・触診・カルテ記載はこの動作を1日に何十回も含む。2時間で4件という頻度と一致する。

## 対策: 発話ゲート（`UtteranceIntentGate`）

録音と ASR は従来どおり走らせ、書き起こしが「アシスタントへの依頼」でなければ
**LLM 呼び出しと TTS 発話に到達させない**。診察室での実害は、マイクが開くことではなく
無関係な応答が読み上げられることだった（誤発火4件のうち3件が応答を生成・発話していた）。

### 日本語・英語だけを通す言語ゲート

2026-09-01 11:50、誤発火の書き起こし `這 因為怎麼吃掉` が従来のCJK判定を
すり抜け、LLMが中国語で応答し診察室でTTSが読み上げた。従来は漢字を日本語の
根拠にしていたため、中国語も「CJKあり」になっていた。同日の11:55は英語幻聴として
既存ゲートで止まったが、文字種をCJK対非CJKに二分する設計では不十分だった。

日本語は未知の言い回しを守るため既定で通す一方、英語は依頼・質問の形を積極的な
通過条件にする。これは履歴100件中の英語書き起こし9種がすべて非依頼の幻聴であり、
実際の英語依頼が0件だったという運用データに基づく。

判定順（`app/src/main/java/com/g150446/voiceharness/UtteranceIntentGate.kt`）:

1. 依頼形・疑問形・アプリコマンド語・会話リセット句 → **無条件 PASS**。
   `ですか` は疑問形に含めるが `です` は含めない（「お疲れ様です」を通してしまうため）。
2. かなを含む → 日本語として後続の相槌・断片判定へ進む。
3. 漢字を含むがかなを含まない、またはハングル・キリル・タイ・アラビア・
   デーヴァナーガリー・ギリシャ・ヘブライ文字を含む → `SUPPRESS_FOREIGN`。
4. ラテン文字を含む → 行頭が英語の依頼動詞・疑問詞・助動詞、または `?` を含む場合だけ
   PASS。それ以外は `SUPPRESS_NON_REQUEST`。
5. 相槌のみ（最長一致で全体を消費できる） → `SUPPRESS_BACKCHANNEL`。
   ただし会話セッションが継続中なら PASS（問い返しへの「はい」を守る）。
6. 日本語10文字以下で格助詞終端 → `SUPPRESS_FRAGMENT`。
7. それ以外は PASS。

セッション継続判定は `AssistantGateway.isConversationActive()`（10分窓）。
**抑制された発話は LLM を呼ばないのでターンを追加せず、セッションを開かない。**
誤発火が次の誤発火の相槌免除を誘発する連鎖は構造的に起きない。

### 組み込み位置

`VoiceProcessor.transcribeAndRespondOnDevice()`、`AsrTextFilter.isGarbageOrEmpty` の直後。
呼び出し元はジェスチャー録音経路のみで、`handleAssistantRequest`（システムアシスタント／
テキスト入力）は通らない。

抑制時は履歴に `errorMessage = "誤発火として抑制: <Verdict>"` を残し、
**書き起こしテキストは消さない**。何を誤認したか追えないとゲートを調整できない。

### 実データによる検証

履歴100件のうち無音を除く54件（意図的コマンド32件 / 非意図22件）を実装コードに通した:

```
blockedIntent=0 / 32     passedJunk=0 / 22
  SUPPRESS_NON_REQUEST  18   ("I'm going to go." "All right." "Thank you." "I'm sorry." "PHONE RINGS")
  SUPPRESS_BACKCHANNEL   2   (「はい、はい。」「はい、お疲れ様です。どうも。」)
  SUPPRESS_FRAGMENT      2   (「老廃物を」「もう本当に」)
```

追加回帰試験では実測中国語 `這 因為怎麼吃掉` とハングルを `SUPPRESS_FOREIGN`、
英語幻聴9種を `SUPPRESS_NON_REQUEST` とし、`What is the weather today?` と
`Set a reminder for 5pm` はPASSすることを固定した。漢字だけの日本語（「血圧」など）を
外国語として止めるリスクは残るが、履歴100件では該当したのは上記中国語の1件だけだった。

**この検証の限界**: 抑制側22件のラベルは表層特徴（英語・擬音・相槌・断片）で人手判定
しており非循環。通過側32件のラベルはキーワード族がゲートと重なるため循環がある。
ゲートが「証拠がなければ通す」設計であることが唯一の担保なので、
**外来1日運用で誤遮断0件を確認するまでが本当の合格判定**。履歴の
`誤発火として抑制:` を後から grep して確認できる。

### 既知のリスク

`SUPPRESS_FRAGMENT` は「明日の天気は」のような短い実クエリを潰しうる（CJK 6文字、
格助詞 `は` 終端）。`？` が付けば疑問形で通る。誤遮断が出たら
`FRAGMENT_MAX_CJK` を下げるか、助詞集合から `は` `が` を外す。

## ダブルタップによる応答中断

誤発火に気づいた時点で止められるよう、`RECORDING` / `TRANSCRIBING` / `RESPONDING` /
`SPEAKING` 中のダブルタップは音声パイプラインの中断として扱う。録音中は Node へ RX stop を
送り、続く TX `0x02` では ASR を走らせない。処理JobとAIバックエンドをキャンセルし、
TTSを停止して状態を `READY` に戻し、画面と履歴に「中断しました」を残す。

処理中でない double はリーダーモードの ON/OFF トグル（ON は G2 接続時のみ。G2 ページ送りは
single）。詳細は [`smart_glasses_output.md`](smart_glasses_output.md)。

残振動で double 直後に single が飛びやすいため、ホストは double 受信から **2 秒間**
single の録音コマンドを送らない（進行中の遅延 start Job も cancel）。Node は double
検出から **1.5 秒** single を emit しない。UI のタップ回数は増えてよい。

リマインダーは永続化とAlarmManager登録が短い同期区間にあるため、Jobキャンセルだけでは
止められない。中断フラグと処理中IDを保持し、登録直前なら打ち切り、登録と中断が競合した
場合はAlarmManagerとリポジトリの両方から削除して巻き戻す。

## 残った課題

誤発火そのものは止まっていない（マイクは開き、ASR は走る）。根本対策には
IMU 生時系列を使った分類が要る。FW には既に軌跡パイプライン（`0x36`/`0x37`/`0x38`、
40 Hz × 6軸 × 9.6秒窓）が実装済みだが `#if GESTURE_DEBUG_HISTORY`（既定 0）で
本番ビルドから落ちている。成功時の flush は録音停止処理の中にあり音声と競合せず、
ASR 完了前に届くため、**発話ゲートと同じ判定点で分類器の判定を使える**。

必要なのはラベル付きデータで、今は1件も無い。収集基盤（実行時フラグでの軌跡有効化、
Android 側のパースとファイル保存、履歴画面でのラベリング）が次の作業。
学習後の Go/No-Go は「正検出維持率95%で誤発火70%以上削減」に置く。達成できなければ
ML では分離できないと結論し、ジェスチャー定義そのものの変更を検討する。

## IMU 軌跡の収集（FW `0.0.91` + Android）

Phase 3 の分類器には**ラベル付きの生 IMU が要る**。FW 側の軌跡パイプラインは以前から
実装されていたが `#if GESTURE_DEBUG_HISTORY`（既定 0）で本番ビルドから落ちていた。
`0.0.91` でこれを既定 1 にし、代わりに**実行時スイッチ**を入れた。

### FW `0.0.91`

- `CMD_SET_GESTURE_CAPTURE`（RX `0x06`、`[0x06, 0/1]`）で収集を切り替える。
  ack は `EVT_GESTURE_CAPTURE`（TX `0x39`、`[0x00,0x55,0x39,enabled]`）を
  `notify_all_conns()` で**全接続へ**（`0x40` と同じ非対称を作らない）。
- **既定 OFF で、RAM にしか持たない。** リセットで消えるため、接続時の greeting でも
  現在値を送り、アプリは接続のたびに再送する。
- 収集 OFF のときは `gesture_trajectory_clear()` が `active` を立てないので、
  push / finish / flush がすべて no-op になる。分岐1つ以外のコストは掛からない。
- `GESTURE_DEBUG_HISTORY=0` の痩せたビルドでも ack は返るが、常に OFF を報告する
  （`gesture_capture_effective()`）。嘘の ack を返さない。
- コスト: 静的バッファ 22.5 KB（`gesture_trajectory` / `gesture_host_collection`
  各 10752 B、`gesture_history` 1536 B）。RAM 171 KB / 256 KB。
  署名イメージ 253799 B（slot 上限 335872 B）。

### 送出タイミングが好都合

成功時の flush は録音停止処理の中（`send_event_packet(0x02)` の直後）で走るので
**音声ストリームと競合しない**。しかも ASR 完了より前に届くため、
将来の分類器は**発話ゲートと同じ判定点**で使える。失敗シーケンス（`result=2`）は
録音自体が無いので即時флush される。正例・負例が同じ経路で揃う。

### Android

- `BleManager` が `0x36`/`0x37`/`0x38` を解釈する。`0x37` は1試行で約48パケット来るので
  hex ダンプ除外リストに追加した。`0x36` の version が想定外なら黙って捨てる。
- **サンプリングは一定ではない。** NodeのIMUポーリングはライトスリープ中50 ms、
  活動中25 ms。`0x36` の `period_ms`（25）は公称値にすぎない（実測: 静止状態で
  6005 ms / 118サンプル ≈ 51 ms間隔）。**特徴量抽出では各サンプルの `t_ms` を使い、
  一定レートを仮定しないこと。** CSVヘッダには実測中央値 `median_period_ms` も書く。
- `GestureTrajectoryStore` がバッチを組み立て、**CSV ファイル**へ書く
  （`filesDir/gesture_trajectories/<entryId>.csv`、上限400件）。
  **SharedPreferences には入れない** — `voice_history_prefs.xml` は既に 625 KB、
  `openrouter_prefs.xml` は 1 MB あり、1件30 KB を100件足すと破綻する。
  `HistoryEntry` はファイル名だけ持つ。
- 1つの軌跡が2つの履歴に付かないよう、`takeForRecording()` は一度取ったら消す。
  `result != 1`（失敗シーケンス）は録音を伴わないので履歴には付かない。

### マイルストーンは Node のバッチを使う

生波形を区間分割（dwell / 挙上 / 回内 / 最終静止）できないと特徴量設計が始まらない。
その境界は `0x33`–`0x35` のマイルストーンバッチが持っている。

**`gesture_history_clear()` と `gesture_trajectory_clear()` は `main.c:2608-2609` で
連続して呼ばれるので、バッチと軌跡は時刻原点を共有する。** これが raw サンプルの中で
「掌下ラッチはどこか」「match はどこか」を特定できる唯一の手段。

一方、ライブ `0x30` を時刻スライスしたものは**電話側の受信時刻**が基準で、BLE の
ジッタ分ずれる。表示には十分だが、サンプルとの位置合わせには使えない。

そこで履歴保存時に **Node のバッチを優先**し、取れなかったときだけライブスライスへ
落とす。どちらを使ったかは `HistoryEntry.diagsFromNodeBatch` に持ち、履歴詳細にも
「Node バッチ（軌跡と時刻軸が一致）」/「ライブ 0x30（軌跡とは別時刻軸）」と出す。
**ずれたマイルストーンで学習しても失敗は静かに起きるだけなので、どちらかを明示する。**

バッチは軌跡と同じく停止イベントの後に届くので、取得は同じく `saveHistoryEntry()` で行う。
軌跡CSVのヘッダにも `# milestone t_ms,stage,reason,v1,v2,v3` 行として埋め込むので、
オフライン側は1ファイルだけ読めばよい（時刻軸が一致するバッチのときだけ書き出す）。

### ラベリング

- 履歴詳細に「意図的 / 誤発火」ボタン。**未判定を第3の状態として残す** —
  判定していないものをどちらかのクラスとして数えてはいけない。
  同じラベルをもう一度押すと未判定へ戻る。
- 履歴一覧に**本日の時間帯一括判定**を置いた。今回ユーザーが手でやったのが
  まさにこの操作で、外来のようにまとまった誤発火を1件ずつ開いてラベルする運用は
  まず続かない。ここが省かれると学習データが集まらない。

### 運用

1. 設定画面の「ジェスチャーIMU収集」をオンにする（Nodeの実報告を併記するので、
   非対応ファームや Node リセットは表示で分かる）。
2. 外来など誤発火が起きる環境で1日使う。
3. 帰宅後、履歴の時間帯一括判定でラベルを付ける。
4. CSV を吸い出す:

```bash
adb -s <device> exec-out run-as com.g150446.voiceharness \
  tar c files/gesture_trajectories > trajectories.tar
tar tvf trajectories.tar    # 中身を確認してから展開する
```

ディレクトリはアプリ起動時に作られる。存在しないと `tar` は**エラーを出さずに
壊れたアーカイブを吐く**ので、`tar tvf` での確認を省かないこと。

5. 収集を**オフに戻す**（常時オンは帯域と電池の無駄）。

### 実機検証で見つけた欠陥（FW `0.0.92` / Android で修正）

`0.0.91` を実機で回して初めて出た。どちらも机上では見えない。

**1. 軌跡がスレッド越しに二重送信される（FW）**

Androidログ:

```
22:17:36.176  0x38 (00 55 38 17 79 01 00)   session=23 sent=377
22:17:36.177  0x38 (00 55 38 16 79 01 00)   session=22 sent=377
Chunk out of order: expected 568, got 288
Chunk out of order: expected 576, got 288   <- 同じ start が2回
```

END が1ms差で2つ、しかも **23→22 の LIFO**。チャンクの start が
`288,288,296,296,...` と厳密に交互。**同一ウィンドウが2セッションとして並行送信**
されていた。

原因は flush が**2スレッドから呼ばれる**こと:

| 呼び出し元 | スレッド |
|---|---|
| `process_motion_sample()`（`main.c:3279`） | main |
| 録音停止処理（`main.c:4318`） | `audio_thread()` |

`flush_trajectory_batch()` はチャンク間で `k_msleep(5)` するため、両者が
その隙間で交互に走った。`atomic_cas` のガードで、実行中の2本目を弾くようにした。
**単なる `bool` では test と set の間で切り替わりうるのでアトミックが要る。**

**2. 軌跡が履歴に一度も紐づかない（Android）**

FW は録音停止時に `send_event_packet(0x02)` を送った**あと**で
`flush_gesture_trajectory()` を呼ぶ（`main.c:4317-4319`）。Android は `0x02` を受けた
瞬間に `capturePendingGestureDiags()` から軌跡を取りに行っていたので、
**約250msのチャンク送信が始まる前**で必ず空振りしていた。CSVは1件も書かれない。

計画時に「ここで取るのは競合ではない」とコメントに書いていたが、事実と逆だった。
録音停止時刻だけを保持し、**ASR完了後の `saveHistoryEntry()` で取得**するよう変更した。

**3. チャンクを追記していた（Android）**

`onChunk` が `start` を無視して末尾に追記していたため、上記の二重送信で
1ウィンドウが 746/377 サンプルに膨れた。プロトコルが `start` を持つのは
**位置指定のため**なので、インデックス指定で格納するようにした。
重複は上書きになり、欠落は `missingSamples` として見える。
